아래는 한 개발자가 한 레포에서 한 작업들의 요약이다. 이것으로 **채용 담당자와 개발자 면접관이 읽을** 두 가지 결과물을 만들어라.
요약과 README에 없는 내용은 쓰지 마라. 숫자는 요약의 facts나 README에 있는 것만 쓸 수 있다.

근거(evidence) 표시 방법:
- 작업에 대한 문장은 근거 커밋 ID(C01 형식)를 붙인다
- 프로젝트가 무엇인지처럼 README·레포 설명에서 온 문장은 "README"를 붙인다

## 문장 쓰는 방법 (모든 결과물에 적용)

읽는 사람이 **무엇을 어떻게 했는지**까지 알 수 있어야 한다. 두루뭉술한 문장은 아예 쓰지 마라.

- 금지: "성능을 개선했다", "사용성을 높였다", "구조를 고도화했다", "안정성을 확보했다", "다양한 기능을 추가했다", "전반적으로 정리했다"처럼 대상과 방법이 없는 문장
- 대신 **대상 + 방법**을 밝힌다. 어떤 화면·함수·파일·API·라이브러리를 어떤 방법으로 바꿨는지 쓴다
  - "렌더링 성능을 개선했다" ✗
  - "같은 제품을 InstancedMesh 하나로 모아 그려 드로우콜을 줄였다" ✓
- 파일·함수·라이브러리 이름은 요약(key_points, decisions, technologies)에 나온 것만 쓴다. 그런 이름이 없으면 바뀐 동작을 구체적으로 쓴다
- 한 문장에는 한 가지만 담는다. "그리고", "및", "등"으로 여러 작업을 묶지 마라
- 같은 내용을 두 칸에 반복하지 마라. 배경은 문제, 한 일은 방법, 결과는 확인된 사실이다

## 1. portfolio: 포트폴리오 소개글 (빠르게 훑어 읽히도록)

- tagline: 프로젝트를 한 줄로 (25자 안팎, 명사형으로 끝냄. 예: "실제 치수 기반 데스크 셋업 시뮬레이터")
- overview: 무엇이고 누구를 위한 것인지, 핵심 기능이 무엇인지 2~3문장
- contributions: 주요 기여 4~6개. significance가 major인 작업 우선, 관련된 작은 작업은 합친다.
  각 기여는 **배경 → 한 일 → 결과** 순서로 읽히게 쓴다. 맥락 없이 바로 구현 얘기로 들어가지 마라
  - title: 기여 제목 (15자 안팎, 예: "three.js 3D 데스크 뷰")
  - background: **배경.** 어떤 문제나 필요가 있었는지 한 문장 + evidence. 요약의 problem을 쓰고, 없으면 그 기능이 왜 필요한지를 쓴다. 해결 방법은 여기 쓰지 않는다
  - summary: **한 일.** 무엇을 어떤 기술로 만들었는지 한 문장 + evidence
  - points: **구현 포인트** 2~3개. 각 한 문장, "무엇을 + 어떤 기술·방법으로" + evidence. 요약의 key_points·decisions를 활용한다
  - outcome: **결과.** 그래서 무엇이 가능해졌는지 한 문장 + evidence. 근거에서 확인되는 것만 쓴다
    (예: "제품 19종을 50단계로 배치할 수 있다", "사설 IP로 가는 요청은 막힌다")
    확인할 수 있는 결과가 없으면 text를 빈 문자열, evidence를 빈 목록으로 두고 지어내지 마라
  - technologies: 이 기여에 쓴 기술 2~5개
- tech_stack: 실제로 쓴 기술을 분야별로 묶는다 (예: "Frontend", "3D·그래픽", "Backend·인프라", "Desktop"). 요약의 technologies와 언어 통계에 있는 것만

## 2. slides: 기술 발표 자료 8~10장 (포트폴리오 면접·기술 발표 수준)

각 장:
- layout: 아래 중 하나
- title: 짧은 제목 (15자 이내)
- headline: **이 장의 핵심 메시지 한 문장** (주장형. 예: "사진 한 장으로 제품을 입체로 보여 주도록 높이 지도를 만들었다")
- points: 2~4개. heading은 굵게 보일 짧은 키워드(10자 이내), text는 한 문장 설명 + evidence
- highlights: 근거가 있는 수치 0~3개를 큰 숫자 카드로 (value 예: "19종", "50단계", label은 무엇의 수치인지). facts에 없는 숫자는 절대 넣지 마라
  - 기능의 규모를 보여주는 수치만 (지원 개수, 종류 수, 단계 수, 제한 값 등). 카메라 거리·픽셀·색상 값 같은 코드 내부 상수는 넣지 마라. 마땅한 수치가 없으면 빈 목록
- flow: architecture 장에서만, 데이터나 처리의 흐름 3~6단계 (예: ["Expo 웹 빌드", "Electron 래퍼", "app:// 프로토콜 로드", "원격 번들 확인"])
- notes: 발표자가 말로 할 내용 2~4문장. 기술적 판단의 이유를 설명하되 근거 없는 성과·수치는 쓰지 마라

순서와 layout:
1. cover: title은 프로젝트 이름, headline은 tagline, points는 비워도 된다
2. agenda: 발표 순서. points의 heading에 각 장 제목, text에 한 줄 설명 (근거 "README" 또는 관련 커밋)
3. problem: 이 프로젝트가 해결하려는 문제/동기
4~7. feature 또는 architecture: 핵심 작업마다 1장. 단순 나열이 아니라 "문제 → 접근 → 구현" 흐름이 보이게. 구조가 핵심인 작업은 architecture로 flow를 채운다
8. tech: 기술 스택과 선택 이유. points의 heading은 분야, text는 쓴 기술과 그 기술로 한 일
9. summary: 정리. 핵심 성과 3개 (근거 있는 것만)

"배운 점", "향후 계획", "성능 향상"처럼 입력으로 확인할 수 없는 내용은 만들지 마라.

## 3. design: 디자인 (네 축을 각각 고른다)

포트폴리오와 발표 자료에 같이 적용된다. 프로젝트의 성격과 분위기를 보고 **축마다 이유를 가지고** 골라라.
무난한 기본값(indigo·light·sans·glow)을 그냥 쓰지 마라.

- **palette** (색 계열): 프로젝트 분야에 맞춰서
  - indigo·violet: 범용 웹 서비스, AI 서비스
  - blue·sky: 업무 도구, 금융, 교육 플랫폼
  - cyan·teal: 데이터 시각화, 대시보드, 지도·여행
  - emerald·green·lime: 개발 도구·CLI, 환경, 건강, 커뮤니티, 게임
  - amber·orange: 소비자 앱, 커머스, 음식, 라이프스타일
  - rose·fuchsia: 소셜, 콘텐츠, 디자인·꾸미기, 엔터테인먼트
  - slate·stone: 미니멀한 도구, 문서, 인프라, 포트폴리오 사이트
- **surface** (본문 배경 톤)
  - light: 흰 배경. 가장 무난하다
  - tint: 고른 색을 아주 옅게 깐 배경. 색을 보여주고 싶을 때
  - paper: 종이빛 배경. 문서·연구·교육·리포트
  - ink: 흰 배경 + 검은 선의 고대비. 미니멀한 도구, 디자인
  - dark: 어두운 화면. CLI, 개발 도구, 백엔드·인프라, 게임
- **font** (글꼴)
  - sans: 기본
  - serif: 명조체. 문서·글쓰기·연구·교육
  - mono: 코드 글꼴. CLI, 개발 도구, 라이브러리, 자동화
  - display: 아주 굵고 큰 제목. 디자인·브랜딩·미니멀
- **cover** (표지·머리말 형식)
  - glow: 그라데이션 + 빛 번짐
  - terminal: 터미널 창 + 깜빡이는 커서
  - paper: 보고서 표지처럼 굵은 가로줄
  - mono: 검은 바탕에 아주 큰 제목

잘 맞는 조합 예:
- 개발 도구·CLI·백엔드 → emerald · dark · mono · terminal
- 연구·문서·교육 → amber · paper · serif · paper
- 데이터·대시보드 → cyan · tint · sans · glow
- 소비자 앱·커머스 → orange · light · sans · glow
- 디자인 시스템·미니멀 도구 → slate · ink · display · mono

서로 어긋나는 조합(예: cover가 terminal인데 surface가 paper, font가 mono인데 surface가 paper)은 피한다.
